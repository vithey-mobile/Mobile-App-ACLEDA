# 01 - Student Verification Form Prompt

Build the **Student Verification submission screen** used to unlock Finance for eligible students, matching `Prompt Frontend/screen image/finance/verify student finance.png` while protecting credentials and student documents.

## Goal

Collect the minimum data required to verify student eligibility, upload a private student-ID document only when the backend supports secure review, submit once, and route according to the authoritative result: pending review, verified, or rejected.

## Critical credential rule

The reference includes a generic **Password** field. The current backend verification request requires only `student_id` and `university_email`; it does not require a password. Do not collect or send a university/Google/email password through this form.

- Preferred production behavior: omit the Password field.
- If security policy requires recent authentication, use a documented Vithey reauthentication/OTP/SSO flow that clearly labels the credential and never sends it to `/students/verify`.
- Never store, log, include in analytics, or attach any password to verification data.
- Do not implement a lookalike university login form.

## Screen composition

Match the reference from top to bottom:

1. **System safe area and back action**
   - White background, dark system icons, and a top-left back arrow.
   - Back returns to the prior safe screen/Finance gate without submitting.

2. **Heading**
   - Left-aligned bold title: **Student Verification**.

3. **Student ID field**
   - Label: **Student ID**.
   - Placeholder: **Enter your student ID**.
   - Use the institution's documented format, capitalization, and length validation.
   - Trim surrounding whitespace but preserve meaningful leading zeros.

4. **Student email field**
   - Label: **Student Email**.
   - Placeholder: **your.email@university.edu**.
   - Use email keyboard/autofill.
   - Validate syntax and an approved university-domain allowlist from configuration/server policy; do not hard-code one domain in widgets.

5. **Credential/reauth slot**
   - The reference shows Password here.
   - Omit it under the current API contract.
   - If a documented Vithey reauthentication mechanism is added, render an explicit **Confirm your Vithey password** or provider reauthentication control in this position with visibility toggle and secure handling.

6. **Student ID document upload**
   - Label: **Upload Student ID**.
   - Large rounded dashed-border upload area.
   - Centered upload icon and text:
     - **Click to upload**
     - **PNG, JPG or PDF (max. 5MB)**
   - Tapping opens a privacy-preserving file/photo picker.
   - After selection, show filename/type/size, preview where safe, Replace, and Remove.
   - Do not display the full student ID number extracted from the image.

7. **Primary action**
   - Full-width teal rounded button: **Verify Student Status**.
   - Use the small trailing circular/arrow icon shown in the reference.
   - Maintain at least `44 px` height and show stable inline loading state.

8. **Review-time information card**
   - Light-gray rounded card with a neutral circular icon.
   - Bold text: **Verification takes 24–48 hours**.
   - Supporting copy: **You’ll receive an email when your student status is verified. Keep shopping in the meantime!**
   - Replace “Keep shopping” with product-appropriate copy such as **You can continue using Vithey in the meantime** unless commerce is truly intended.
   - Only promise 24–48 hours/email notification if the backend implements asynchronous review and notifications.

## Form validation

- Student ID: required, normalized through documented institution rules.
- University email: required, valid, approved domain.
- Document: required only when secure document-review flow is enabled.
- Password: never required by the current verification endpoint.
- Reject unsupported MIME, corrupt files, files above 5 MB, or unsafe content before upload.
- Verify MIME from file bytes/server inspection, not extension alone.
- Show inline field errors and focus/scroll to the first invalid input.
- Do not start an upload if basic field validation fails.

## Document security

Student ID documents are highly sensitive:

- Add a private file category such as `STUDENT_ID` to file-service before enabling uploads.
- Store in a private bucket/object ACL; never expose as public post media.
- Only the submitting user and authorized verification reviewers/services can access it.
- Use short-lived authenticated/signed preview URLs.
- Define encryption, malware scanning, audit logs, retention, deletion after review, and reviewer authorization.
- Remove EXIF/location metadata where appropriate.
- Never cache the document in shared preferences, gallery, logs, crash reports, or analytics.
- Clean temporary local copies after upload/submission/discard according to platform policy.

If these guarantees are not implemented, feature-gate the upload field and use the current email/ID verification contract only; never pretend a document was reviewed.

## Submission behavior

Use a guarded state machine:

`editing → validating → uploadingDocument → submittingVerification → pending|verified|rejected|error`

1. Freeze an immutable form snapshot.
2. Prevent duplicate submissions.
3. Validate current authoritative verification state; do not create a second pending request.
4. Upload document once when required and obtain `document_file_id`.
5. Submit verification with an idempotency key.
6. Clear sensitive temporary files after the documented terminal point.
7. Route by server response:
   - `PENDING` → `Routes.VERIFICATION_STATUS`.
   - `VERIFIED` → refresh auth/user claims, then Finance or success status.
   - `REJECTED` → status screen with reason/retry rules.
8. On retry after a successful upload, reuse the secure file ID rather than uploading duplicates.

## Request contract

Current documented request:

```json
{
  "student_id": "AUB2024001",
  "university_email": "student@aub.edu.kh"
}
```

Target asynchronous document-review request if approved:

```json
{
  "student_id": "AUB2024001",
  "university_email": "student@aub.edu.kh",
  "document_file_id": "uuid"
}
```

No password belongs in either payload.

## Current backend contract gaps

The image and current auth-service contract describe different workflows:

1. Backend currently verifies email/domain immediately and promotes the user to `STUDENT`; the UI promises manual review in 24–48 hours.
2. Backend has no student-document field or private `STUDENT_ID` file type.
3. Backend exposes no verification-status GET endpoint for pending/rejected timelines.
4. Backend does not document rejection reason, resubmission, reviewer actions, or notifications.
5. Role-changing token refresh/claim propagation after verification is not defined.
6. Idempotent duplicate-submission behavior is not defined.

Choose and document one production workflow:

- **Immediate verification:** collect only Student ID + university email, omit document/review-time copy, and route verified users after server success.
- **Asynchronous document review:** extend auth/file services with document submission, `PENDING|VERIFIED|REJECTED` status reads, reviewer workflow, notification, retention, and role refresh.

Do not mix the visual promise of asynchronous review with an endpoint that immediately verifies without document review.

## Loading and errors

- Upload progress is distinct from verification submission progress.
- Permission/file-picker cancellation returns to the form without an error banner.
- Upload failure preserves fields and offers Retry/Replace.
- Submission failure preserves the uploaded secure file reference for safe retry.
- Duplicate pending request routes to status instead of showing a generic error.
- Already verified routes to Finance/status success.
- Rejected responses show actionable, non-sensitive reason and retry eligibility.
- Rate limiting displays a retry time when provided.
- Never expose raw file paths, tokens, stack traces, or internal reviewer notes.

## Draft and back behavior

- Preserve non-sensitive Student ID/email draft during temporary picker navigation.
- Do not persist password values.
- Ask before discarding a selected sensitive document/local draft on Back.
- Clear temporary sensitive files after explicit discard.
- Do not mark verification complete locally before authoritative success.

## Accessibility

- Label Back, every field, upload/drop zone, selected document, Replace/Remove, Verify button, loading, and information card.
- Announce validation and server errors.
- Provide document type/size in semantics without reading the full local path.
- Ensure `44 × 44` minimum targets.
- Support keyboard traversal and text scaling without overflow.
- Do not rely on color alone for invalid, uploading, pending, or success states.

## Testing and acceptance criteria

- Screen matches `verify student finance.png`: title, Student ID/email, upload area, teal Verify button, and information card.
- Generic/university Password is never collected or sent under the current contract.
- Student ID/email validation and configured domain rules work.
- PNG/JPG/PDF and 5 MB validation work when document review is enabled.
- Sensitive documents use private storage and are never exposed via public URLs/logs.
- Duplicate submit, picker cancellation, upload failure/retry, submit failure/retry, already pending, already verified, and rejected states are tested.
- Immediate and asynchronous workflow flags cannot produce contradictory UI promises.
- Successful result routes according to authoritative status and refreshes role claims where needed.
- No overflow occurs on small phones, large text, keyboard open, or long validation messages.
