# 02 - Student Verification Status Prompt

Build the **Student Verification Status** module for Vithey in Flutter. It must represent the complete verification lifecycle while matching the supplied pending, verified, and not-verified references.

## Visual references

- Main pending screen: `Prompt Frontend/screen image/finance/pending verify.png`
- Verified status card: `Prompt Frontend/screen image/finance/verify success.png`
- Not-submitted status card: `Prompt Frontend/screen image/finance/verify unsuccess.png`
- Submission form: `Prompt Frontend/screen image/finance/verify student finance.png`

The `verify unsuccess.png` copy says the user has not submitted verification, so it represents **Not Submitted**, not a failed/rejected review. Create a separate rejected state with truthful reason/retry behavior.

## Goal

Give the student one authoritative place to understand whether verification has not been submitted, is under review, succeeded, or was rejected; show the submitted document safely; support contact/retry; and unlock Finance only after verification and finance-account provisioning are ready.

## Verification state machine

Use a server-backed enum:

```dart
enum VerificationStatus {
  notSubmitted,
  pending,
  verified,
  rejected,
}
```

Optional separate provisioning state:

```dart
enum FinanceProvisioningStatus {
  unknown,
  provisioning,
  ready,
  failed,
}
```

Allowed transitions:

- `NOT_SUBMITTED → PENDING` after asynchronous submission.
- `NOT_SUBMITTED → VERIFIED` only for an explicitly documented immediate-verification flow.
- `PENDING → VERIFIED` after approval.
- `PENDING → REJECTED` after review.
- `REJECTED → PENDING` after an allowed resubmission.
- `VERIFIED` is not downgraded by stale local/cache data.

Never infer verified status only from a locally completed form or uploaded file.

- Short status-specific subtitle.

## Pending state

Match `pending verify.png`.

### Header copy

- Title: **Verification Status**.
- Subtitle: **Your verification is pending**.

### Pending status card

- Large rounded orange-to-red gradient card.
- Centered circular translucent icon area with an in-progress spinner/clock mark.
- Bold white heading: **Verification Pending**.
- Supporting white text: **Your application is under review**.
- Spinner is a status illustration, not an endlessly blocking loading indicator; screen content remains usable.

### Verification Timeline

- Section heading: **Verification Timeline**.
- Three vertically arranged stages with icons/connector treatment:
  1. **Application Submitted** — completed green, server submission date.
  2. **Under Review** — active orange, e.g. **In progress…**.
  3. **Verification Complete** — inactive gray, **Pending**.
- Dates/statuses come from the server. Do not hard-code `June 1, 2026`.
- Accessibility announces current stage and **Step 2 of 3**.

### Submitted Documents

- Rounded bordered section titled **Submitted Documents**.
- Row: upload/document icon, **Student ID Card**, green **Uploaded** status.
- Tapping may open an authenticated, short-lived preview only if policy permits.
- Never expose a permanent public URL, local path, full student number, or reviewer-only metadata.

### What happens next?

- Light-blue rounded information card.
- Heading: **What happens next?**
- Explain that authorized reviewers are checking the submitted data and that the user will receive an email/in-app notification after completion.
- Show **24–48 hours** only if it is a real service-level expectation; otherwise use server/configured wording.

### Contact Support

- Full-width teal rounded button: **Contact Support**.
- Open the app's defined support/chat/help channel with verification request ID context, but do not prefill sensitive documents or student identifiers into third-party tools.

## Not Submitted state

Use `verify unsuccess.png` as the compact status-card reference:

- Dark slate rounded card.
- Centered circular neutral icon with an X/empty mark.
- White heading: **Not Verified**.
- Supporting copy: **You haven’t submitted your verification yet**.
- Add a clear teal **Verify Student Status** action below the card that opens `Routes.STUDENT_VERIFICATION`.
- Do not describe this state as rejected or failed.

## Verified state

Match `verify success.png`:

- Large rounded green status card.
- Centered translucent circle with shield/check icon.
- Bold white heading: **Verified Student**.
- Supporting text: **Your student status has been confirmed**.
- Below the card:
  - Show verified date when available.
  - Primary teal/green action: **Continue to Finance**.
- Refresh authoritative auth state/claims before opening Finance.
- If finance account provisioning is still in progress, show **Setting up your finance account…** with Retry and keep the verified success state; do not send the user back to verification.

## Rejected state

Rejected is distinct from Not Submitted and needs its own truthful UI:

- Red/amber rounded status card with a clear warning icon.
- Heading: **Verification Unsuccessful** or **Verification Needs Attention**.
- Show a user-safe rejection reason from a documented reason code, for example unreadable document or email mismatch.
- Never display internal reviewer notes.
- Explain whether/when resubmission is allowed.
- Primary action: **Update and Resubmit** when eligible.
- Secondary action: **Contact Support**.
- If resubmission is not currently allowed, disable it with an accessible reason and provide support.

## Refresh, polling, and notifications

- Load authoritative status when the screen opens/resumes and on pull-to-refresh.
- For Pending, use conservative polling only while the screen is visible, with exponential/backoff and app lifecycle awareness.
- Prefer push/in-app notification to inform the user of completion.
- Stop polling on Verified/Rejected, screen disposal, app background, logout, or repeated failures.
- Avoid aggressive background polling and duplicate requests.
- If cached state is shown, mark it stale until refresh completes.

## Verified role/token propagation

Approval changes the user from `USER` to `STUDENT`. Existing JWT claims may remain stale.

After receiving Verified:

1. Refresh the session/token through the documented auth refresh flow or force a safe reauthentication if role-changing refresh is unsupported.
2. Fetch `GET /api/v1/auth/me` and confirm `is_student_verified`/role.
3. Update the global auth/user store.
4. Ask Finance for readiness/data.
5. Navigate to Finance only when authorized; handle event-driven provisioning delay separately.

Never edit the JWT or set a local role manually.

## Finance provisioning

The finance-service consumes `student.verified` asynchronously to create/link the student's finance account. Approval and Finance readiness may not be simultaneous.

- Verified + Finance ready → Continue to Finance.
- Verified + provisioning → show setup message, background retry, manual Retry.
- Verified + provisioning timeout/failure → keep Verified state and offer Contact Support.
- Never downgrade to Not Submitted because Finance returns `403`/empty during propagation.
- Backend should provide a readiness/idempotency contract or a distinguishable provisioning response.

## Submitted document handling

- Retrieve only document metadata required for this screen.
- Preview/download requires ownership and authenticated short-lived access.
- Do not save sensitive documents to public media/gallery automatically.
- Respect retention/deletion policy after approval/rejection.
- Remove local cached previews on logout/account switch.
- Screenshot prevention may be used only when institutional policy requires it.

## Backend API and required additions

Current contract has:

- `POST /api/v1/students/verify`.
- `GET /api/v1/auth/me`.
- Stored status enum `PENDING|VERIFIED|REJECTED`.

The status UI requires a documented authenticated read contract, for example a typed repository method:

```dart
Future<StudentVerification> getMyVerification();
```

The response must include, as applicable:

- Verification ID.
- Status.
- Submitted/updated/verified/rejected timestamps.
- Safe rejection reason code/message.
- Resubmission eligibility/date.
- Submitted document metadata/file ID.
- Notification/review expectation text or configuration.

Also define:

1. Status endpoint/path and caching semantics.
2. Document-review workflow and private file authorization.
3. Reviewer approval/rejection actions.
4. Resubmission/idempotency rules.
5. Email/push notification behavior.
6. Role-changing token refresh behavior.
7. Finance-account provisioning readiness/failure behavior.

Do not invent production paths or show a pending timeline based solely on local timers.

## Loading, empty, and errors

- Initial loading: status-card/timeline skeleton, not a blank screen.
- Offline with cache: show last known status with stale indicator and Retry.
- No verification record: map to Not Submitted.
- Status error: inline/full error with Retry; do not map network failure to Not Verified.
- Unauthorized: global auth refresh/sign-in flow.
- Document preview error: keep status usable and show inline retry.
- Support launch error: show alternative approved contact instructions.
- Never expose raw APIs, tokens, reviewer identities, or stack traces.

## Controller behavior

Implement:

- `startPendingPolling()` / `stopPendingPolling()`.
- `openSubmittedDocument()`.
- `startOrRetryVerification()`.
- `contactSupport()`.

Use one shared observable status source across Finance gate, form, and status screen. Guard navigation so a status update cannot open duplicate Finance routes.

## Accessibility

- Announce current status and timeline step when it changes.
- Add semantic labels for Back, status icon/card, timeline, document row, Retry/Resubmit, Contact Support, and Continue to Finance.
- Do not communicate state through color alone.
- Ensure `44 × 44` targets and sufficient contrast.
- Support text scaling, screen readers, and reduced motion; replace animated spinner with a static in-progress symbol when reduced motion is enabled.
- Restore focus appropriately after refresh/dialog/preview.

## Navigation

| State/action | Destination |
|---|---|
| Not Submitted → Verify | Student Verification form |
| Pending → Back | Prior safe screen |
| Pending/Rejected → Contact Support | Support flow |
| Rejected → Resubmit | Verification form prefilled with non-sensitive values |
| Verified + Finance ready | Finance Home |
| Verified + provisioning | Stay on status with Retry |

Use route replacement where needed so Back cannot return to stale form/pending states after approval.

## Testing and acceptance criteria

- Pending state matches `pending verify.png`: orange card, three-stage timeline, submitted document, next-steps card, and Contact Support.
- Verified card matches `verify success.png` and refreshes authoritative role before Finance.
- Not Submitted card matches `verify unsuccess.png` and opens the form.
- Rejected uses its own actionable state and never reuses misleading not-submitted copy.
- Status/network error is never interpreted as Not Verified.
- Pending polling starts/stops with visibility/lifecycle and transitions once without duplicate navigation.
- Verified-but-provisioning remains verified and retries Finance safely.
- Sensitive document preview is authorized/private and cleaned up correctly.
- Offline cache, stale indicator, refresh, notification update, role refresh, resubmit eligibility, and support are tested.
- No overflow occurs with small devices, large text, long rejection messages, or localization.
