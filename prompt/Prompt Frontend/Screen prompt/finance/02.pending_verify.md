Build the **Student Verification Status** module for Vithey in Flutter. It must represent the complete verification lifecycle while matching the pending layout and status hero cards.

### Status hero cards (`Verified.png`)

Shared style: linear gradient card, centered translucent circle, **white outline clock** (or status icon), white title + subtitle.

| Status | Gradient | Title | Subtitle |
| --- | --- | --- | --- |
| Pending | Orange → red-orange | **Verification Pending** | Your application is under review. |
| Verified | Lime → green | **Verified Success** | Your application has been confirmed. |
| Not submitted | Linear grey | **Not Verified** | You haven't submitted your application yet. |

Rejected keeps a distinct amber/red card with a safe reason (not the grey “Not Verified” card).

### Submission → status mapping (document gate — current app/dev)

| Condition | Flow |
| --- | --- |
| Empty / incomplete ID or email | Stay on form (validation). |
| ID + email, **no** document | Submit → **Pending** briefly → **Not Verified** (fail) + **Verify again** |
| ID + email + **document** | Submit → **Pending** briefly → **Verified Success** |

**Verify again** opens the verification form and prefills prior Student ID / email (and document name when stored). Clearing upload clears stored document. Always allow re-submit; do not skip submission because of a prior local success.

## Goal

Give the student one authoritative place to understand whether verification has not been submitted, is under review, succeeded, or was rejected; show the submitted document safely; support contact/retry; and unlock Finance only after verification and finance-account provisioning are ready.

## Verification state machine

Use a server-backed enum:

`dart
enum VerificationStatus {
  notSubmitted,
  pending,
  verified,
  rejected,
}
`

Optional separate provisioning state:

`dart
enum FinanceProvisioningStatus {
  unknown,
  provisioning,
  ready,
  failed,
}
`

Allowed transitions:

- `NOT_SUBMITTED → PENDING` after asynchronous submission.
- `NOT_SUBMITTED → VERIFIED` only for an explicitly documented immediate-verification flow.
- `PENDING → VERIFIED` after approval.
- `PENDING → REJECTED` after review.
- `REJECTED → PENDING` after an allowed resubmission.
- `VERIFIED` is not downgraded by stale local/cache data.

Never infer verified status only from a locally completed form or uploaded file.

## Not Submitted state

Use grey **Not Verified** hero from `Verified.png`:

- Linear grey card; translucent circle + outline clock / empty mark.
- Title: **Not Verified**
- Subtitle: **You haven't submitted your application yet.** (or equivalent mock copy)
- Clear action: **Verify Student Status** / **Verify again** → form route.
- Do not describe this state as rejected or failed when the user simply has not submitted (or failed the document gate without a server rejection reason).

## Verified state

Match green **Verified Success** hero:

- Lime → green gradient card; shield/check or shared clock chrome with verified copy.
- Title: **Verified Success** (or **Verified Student** if product prefers — keep mock spelling consistent with `Verified.png`).
- Supporting: **Your application has been confirmed.**
- Below: verified date when available; primary action **Continue to Finance**.
- Refresh authoritative auth state/claims before opening Finance.
- If finance account provisioning is still in progress, show **Setting up your finance account...** with Retry and keep the verified success state; do not send the user back to verification.

## Rejected state

Rejected is distinct from Not Submitted:

- Red/amber rounded status card with a clear warning icon.
- Heading: **Verification Unsuccessful** or **Verification Needs Attention**.
- Show a user-safe rejection reason from a documented reason code.
- Never display internal reviewer notes.
- Explain whether/when resubmission is allowed.
- Primary: **Update and Resubmit** / **Verify again** when eligible.
- Secondary: **Contact Support** / Contact the admin.
- If resubmission is not allowed, disable with an accessible reason and provide support.

## Refresh, polling, and notifications

- Load authoritative status when the screen opens/resumes and on pull-to-refresh.
- For Pending, use conservative polling only while the screen is visible, with exponential/backoff and app lifecycle awareness.
- Prefer push/in-app notification to inform the user of completion.
- Stop polling on Verified/Rejected, screen disposal, app background, logout, or repeated failures.
- Avoid aggressive background polling and duplicate requests.
- If cached state is shown, mark it stale until refresh completes.

## Verified role/token propagation

Approval changes the user from `USER` to `STUDENT`. Existing JWT claims may remain stale.

After receiving Verified:

1. Refresh the session/token through the documented auth refresh flow or force a safe reauthentication if role-changing refresh is unsupported.
2. Fetch `GET /api/v1/auth/me` and confirm `is_student_verified`/role.
3. Update the global auth/user store (and any `StudentVerificationRepository.isVerified` Rx used by Home/Profile).
4. Ask Finance for readiness/data.
5. Navigate to Finance only when authorized; handle event-driven provisioning delay separately.

Never edit the JWT or set a local role manually.

## Finance provisioning

The finance-service consumes `student.verified` asynchronously to create/link the student's finance account. Approval and Finance readiness may not be simultaneous.

- Verified + Finance ready → Continue to Finance.
- Verified + provisioning → show setup message, background retry, manual Retry.
- Verified + provisioning timeout/failure → keep Verified state and offer Contact Support.
- Never downgrade to Not Submitted because Finance returns `403`/empty during propagation.
- Backend should provide a readiness/idempotency contract or a distinguishable provisioning response.

Home AppBar finance affordance (dollar circle) and Finance gate should only appear when verification is authoritatively true.

## Submitted document handling

- Retrieve only document metadata required for this screen.
- Preview/download requires ownership and authenticated short-lived access.
- Do not save sensitive documents to public media/gallery automatically.
- Respect retention/deletion policy after approval/rejection.
- Remove local cached previews on logout/account switch.
- Screenshot prevention may be used only when institutional policy requires it.

## Backend API and required additions

Current contract has:

- `POST /api/v1/students/verify`.
- `GET /api/v1/auth/me`.
- Stored status enum `PENDING|VERIFIED|REJECTED`.

The status UI requires a documented authenticated read contract, for example:

`dart
Future<StudentVerification> getMyVerification();
`

The response must include, as applicable:

- Verification ID.
- Status.
- Submitted/updated/verified/rejected timestamps.
- Safe rejection reason code/message.
- Resubmission eligibility/date.
- Submitted document metadata/file ID.
- Notification/review expectation text or configuration.

Also define:

1. Status endpoint/path and caching semantics.
2. Document-review workflow and private file authorization.
3. Reviewer approval/rejection actions.
4. Resubmission/idempotency rules.
5. Email/push notification behavior.
6. Role-changing token refresh behavior.
7. Finance-account provisioning readiness/failure behavior.

Do not invent production paths or show a pending timeline based solely on local timers in production builds. Dev mocks may simulate Pending → Verified/Not Verified for UI walkthroughs.

## Loading, empty, and errors

- Initial loading: status-card/timeline skeleton, not a blank screen.
- Offline with cache: show last known status with stale indicator and Retry.
- No verification record: map to Not Submitted.
- Status error: inline/full error with Retry; do not map network failure to Not Verified.
- Unauthorized: global auth refresh/sign-in flow.
- Document preview error: keep status usable and show inline retry.
- Support launch error: show alternative approved contact instructions.
- Never expose raw APIs, tokens, reviewer identities, or stack traces.

## Accessibility

- Announce current status and timeline step when it changes.
- Add semantic labels for Back, status icon/card, progress steps, document row, Retry/Resubmit, Contact Support, and Continue to Finance.
- Do not communicate state through color alone.
- Ensure `44 × 44` targets and sufficient contrast (light/dark).
- Support text scaling, screen readers, and reduced motion; replace animated spinner with a static in-progress symbol when reduced motion is enabled.
- Restore focus appropriately after refresh/dialog/preview.

## Navigation

| State/action | Destination |
|---|---|
| Not Submitted → Verify | Student Verification form |
| Pending → Back | Prior safe screen |
| Pending/Rejected → Contact Support | Support flow (when shown) |
| Rejected / document-fail → Resubmit / Verify again | Verification form prefilled with non-sensitive values |
| Verified + Finance ready | Finance Home |
| Verified + provisioning | Stay on status with Retry |

Use route replacement where needed so Back cannot return to stale form/pending states after approval.

## Testing and acceptance criteria

- Pending matches **Verification Status Screen.png**: AppBar, heading, orange card, three steps, documents, light-grey next-steps.
- AppBar title is **Verification** (start-aligned) + search; page title is **Verification Status**.
- Card title spelling is **Pending**; step-2 copy **In progressing...**; section title **Verification Status**.
- Verified / Not Verified heroes match **Verified.png**; rejected is truthful and separate.
- Status/network error is never interpreted as Not Verified.
- Pending polling starts/stops with visibility/lifecycle; no duplicate Finance navigation.
- Verified-but-provisioning remains verified and retries Finance safely.
- Document preview is authorized/private and cleaned up correctly.
- Offline cache, stale indicator, refresh, role refresh, resubmit eligibility, and support are covered.
- No overflow on small devices, large text, long rejection messages, or localization.
- Dark mode readable; `flutter analyze` clean on touched files.
