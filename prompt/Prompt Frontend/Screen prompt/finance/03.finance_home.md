## Goal

Show a verified student their total outstanding balance, next due payment, payment receipts/history, and secure invoice detail/download. Users who are not verified must be routed to the appropriate verification state instead of receiving a broken Finance screen.

## Access gate

Before loading finance data:

1. Read the current auth/user state from the authenticated session and `GET /api/v1/auth/me` when needed.
2. Route by verification state:
   - `NOT_SUBMITTED` → student verification form.
   - `PENDING` → verification-status screen.
   - `REJECTED` → verification-status screen with retry guidance.
   - `VERIFIED` / role `STUDENT` → Finance Home.
3. Finance-service still enforces `STUDENT` server-side; UI gating is not authorization.
4. If finance returns `403`, refresh the authoritative verification/role state once. Do not loop between screens.
5. A newly verified student may briefly wait for finance-service account provisioning. Show **Setting up your finance account…** with Retry instead of incorrectly marking them unverified.

## Full screen composition

### 1. System and app bar

- White background and dark status-bar icons.
- Respect `SafeArea`.
- App bar:
  - Small Vithey logo at left.
  - Centered bold title **Finance**.
  - Notification bell at right.
- Use a subtle bottom divider and accessible `44 × 44` action targets.

### 2. Finance summary card

Match the large teal card in `finance home.png`:

- Rounded teal rectangle with comfortable internal padding.
- Upper-left label. The reference says **TOTAL PAYCHECK**, but this value represents money owed; use accurate production copy such as **TOTAL DUE** or **TOTAL PAYABLE**.
- Large currency-formatted total, e.g. `$8,450.00`; fixture values must not be hard-coded.
- Upper-right rounded light-teal badge such as **Due in 14 Days**.
- Lower-left: **Next Due Date** and formatted date.
- Lower-right: **Status** and normalized display status such as **Not Yet Paid**, **Paid**, or **Overdue**.

Summary rules:

- Calculate totals using decimal/minor-unit money types, never binary floating point.
- Group/sum only compatible currencies. If both USD and KHR exist, display separate totals or use a backend-provided normalized summary; never add them directly.
- Total due should include unpaid/overdue assigned fees according to the documented finance rule.
- Next due item is the earliest unpaid due date.
- Days remaining are calculated from server dates using the intended campus/user timezone.
- The backend alert endpoint currently covers seven days, while the reference shows 14 days. Compute the 14-day badge from payment due dates or extend the contract; do not mislabel a seven-day alert.

### 3. Payment Receipts section

- Left heading: **Payment Receipts**.
- Right teal action:
  - Collapsed: **See All**.
  - Expanded: **See Less**.
- Collapsed Home shows the first four most relevant/recent items as in `finance home.png`.
- Expanded state matches `finance show more.png` and shows all loaded items in the same screen, with pagination as needed.
- Keep Finance active in the bottom navigation in both states. The show-more reference incorrectly highlights/labels Chatbot; treat that as a mockup error.

### 4. Receipt row

Each rounded light-gray row contains:

- Left circular money icon:
  - Green for paid.
  - Pink/red for pending/unpaid/overdue.
- Center:
  - Fee name in bold, e.g. Library Fine, School Fee, Housing, Trip.
  - Relevant date below in muted text.
- Right:
  - Currency-formatted amount in bold.
  - Small status pill below.

Map backend states consistently:

| Backend | Display | Style |
|---|---|---|
| `PAID` | Paid | Green |
| `UNPAID` | Pending or Not Paid | Pink/neutral warning |
| `OVERDUE` | Overdue | Red/high emphasis |

Use one approved term throughout the app; do not call an unpaid item a completed receipt in accessibility copy. If this list includes both paid and unpaid items, a clearer production heading is **Payments & Fees**, while preserving the reference layout.

Tapping a row opens the invoice/payment preview for that exact `payment_id`.

### 5. Bottom navigation

Use the shared Home shell navigation:

1. Home.
2. Finance — active teal.
3. Raised center Create action.
4. Chat.
5. Profile.

Preserve state when switching tabs and do not re-fetch repeatedly within a short freshness window.

## Invoice/payment preview

Tapping a payment row opens the dedicated invoice surface defined in `04.detail_invoice.md` using the stable owned `paymentId`. Finance Home owns selection/navigation; Invoice Detail owns breakdown, PDF download, and its loading/error states.

## Data loading and state

Implement:

- `loadFinanceHome()` — summary plus first payment page.
- `refreshFinance()` — pull-to-refresh summary and history.
- `toggleShowAll()` — expand/collapse without losing loaded data.
- `loadMorePayments()` — paginated history in expanded mode.
- `openPaymentDetail(paymentId)`.
- `downloadInvoice(paymentId)`.
- `retryProvisioning()` for newly verified accounts.

States:

- Access/verification check.
- Provisioning.
- Initial skeleton loading.
- Loaded summary/list.
- Empty finance account.
- Initial error.
- Refreshing.
- Pagination loading/error.
- Detail loading/error.
- Invoice download progress/error/success.

Do not block the entire screen when only invoice download or pagination fails.

## Backend API

Current documented endpoints:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/auth/me` | Authoritative role/verification gate |
| `GET` | `/api/v1/payments` | Paginated payment history |
| `GET` | `/api/v1/payments/{id}` | Owned payment detail |
| `GET` | `/api/v1/payments/alerts` | Due/overdue alerts |
| `GET` | `/api/v1/fees` | Assigned fees |
| `GET` | `/api/v1/fees/categories` | Fee categories |

### Required contract additions

The reference requires data not present in the current finance contract. Define it before production rather than inventing values:

1. Finance summary/aggregation or enough paginated-complete data to compute total due reliably.
2. Transaction/invoice reference.
3. Payment breakdown: base amount, processing fee, late charges, and authoritative total.
4. Invoice PDF endpoint/file ID and download authorization.
5. Clear date semantics for paid date vs due date in each state.
6. Stable pagination metadata and ordering.
7. Provisioning state for newly verified students.

Suggested typed repository boundaries:

```dart
Future<FinanceDashboard> getFinanceDashboard();
Future<Paginated<PaymentSummary>> getPayments(PageRequest page);
Future<PaymentInvoice> getPaymentInvoice(String paymentId);
Future<DownloadedFile> downloadInvoice(String paymentId);
```

Do not silently invent production endpoint paths for missing invoice/summary capabilities.

## Models

Use typed models such as:

- `Money { amountMinor, currency }`.
- `FinanceDashboard { totalsByCurrency, nextDuePayment, daysRemaining }`.
- `PaymentSummary { id, feeName, amount, status, dueDate, paidAt }`.
- `PaymentInvoice { transactionRef, breakdown, total, invoiceFileId }`.

Do not parse formatted currency strings back into numeric values.

## Refresh and cache

- Pull-to-refresh from Finance Home.
- Cache the last successful dashboard/list for fast tab restoration, scoped to the current user.
- Mark stale data and refresh in the background.
- Clear finance caches on logout/account switch.
- Never store invoice PDFs or finance payloads in unprotected shared preferences.

## Empty and error behavior

- No assigned fees/payments: show a neutral empty state, not `$0` plus fake receipt rows.
- Partial failure: show available summary/list and an inline retry for the missing section.
- Offline: show cached data with a stale indicator when available.
- `401`: use global token refresh/auth flow.
- `403`: re-evaluate verification/role once and route appropriately.
- `404` payment detail: close/replace preview with **Payment no longer available**.
- Never expose raw backend messages, database IDs beyond approved references, or stack traces.

## Accessibility

- Label Finance title, notifications, summary values, See All/Less, each receipt, statuses, invoice close/download, and bottom navigation.
- Announce amounts with currency and status, not color alone.
- Ensure `44 × 44` minimum targets.
- Keep invoice sheet focus trapped while open and return focus to the originating receipt on close.
- Support text scaling and screen readers without clipping amount/status columns.
- Provide semantic progress for PDF download.

## Responsive and security requirements

- Support phones down to `320 px`, large text, and long localized fee names.
- Allow content scrolling while keeping bottom navigation safe.
- Constrain layout on tablets.
- Avoid logging finance amounts, invoice references, URLs, or student identifiers.
- Enforce ownership server-side on every detail/download.
- Prevent screenshots only if institutional policy explicitly requires it; otherwise do not surprise users.

## Testing and acceptance criteria

- Finance Home matches `finance home.png`: app bar, teal summary, four collapsed receipts, See All, and Finance-active bottom navigation.
- Expanded list matches `finance show more.png`, but Finance remains the active nav item.
- Receipt status/amount/date map from backend values and support USD/KHR correctly.
- See All/Less does not refetch or lose scroll unnecessarily.
- Invoice preview matches `preview invoice.png` and uses authoritative breakdown data.
- Download handles authentication, progress, errors, and ownership safely.
- Not-submitted, pending, rejected, verified, and provisioning gates route correctly without loops.
- Pagination, refresh, empty, partial error, offline cache, and logout cache clearing are tested.
- No overflow occurs with small screens, large text, long fee names, or large amounts.
