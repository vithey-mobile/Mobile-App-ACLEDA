# Upload CV and Apply for Job Prompt

Build the **Upload CV and Apply for Job** flow for the Vithey App in Flutter, matching the supplied reference and connecting it directly to the **Apply** button on a Home job-poster card.

## Visual reference

- `Prompt Frontend/screen image/upload cv/upload_cv.png`
- Reference canvas: approximately `290 × 605 px` (portrait mobile)
- Treat the image as the source of truth for the clean layout: back/title header, compact job context, large whitespace, dashed upload zone, and full-width Submit action.
- Recreate the screen responsively; do not hard-code the reference coordinates.

## Quick info

| Field | Value |
|---|---|
| Screen ID | `12A` |
| Route | `Routes.APPLY_CV` |
| Origin | Job-poster Apply action on Home or Post Detail |
| Flutter module | `lib/modules/apply_cv/` |
| Backend services | `content-service`, `file-service`, `career-service` |
| Auth required | Yes |
| Required post type | `JOB` |

This prompt is the single source of truth for the Upload CV / Apply Job flow.

## Goal

Allow an eligible user to open a specific job from its poster, select or upload a valid CV, review the target job, submit exactly one application, and return a structured success result so the Home job card changes from **Apply** to **Applied**.

## Entry from a job poster

The job-poster card must navigate using a stable post ID:

```dart
Get.toNamed(
  Routes.APPLY_CV,
  arguments: ApplyCvArgs(jobPostId: post.id),
);
```

Rules:

- Pass the canonical `jobPostId`; do not use the poster image, QR code, caption text, or list index as identity.
- Tapping Apply must stop event propagation so it does not also open Post Detail.
- Home should not navigate when its known state is `Applied`, `Closed`, `Expired`, `Full`, or the current user owns the job.
- The Apply CV screen must still revalidate all conditions server-side because route state can be stale or deep-linked.
- Do not pass a mutable full post model as the only source of truth. A lightweight preview may be supplied for instant rendering, followed by an authoritative refresh by ID.

## Screen composition

### 1. System and app bar

- White background with dark status-bar icons.
- Respect `SafeArea`.
- Top app bar:
  - Left back arrow.
  - Bold title: **Upload CV**.
  - Subtle bottom divider.
- Back returns to the originating job card/detail and preserves Home scroll position.

### 2. Job context area

The reference shows the generic copy **What’s happening?** beneath the header. Replace it with useful dynamic job context while preserving the same compact area:

- **Applying for {job title}**.
- Organization/author name.
- Optional deadline/status summary.

If authoritative job data is still loading, show a compact skeleton. If loading fails, show Retry and keep Submit disabled. Never let the user apply to an unidentified job.

### 3. Job description and application note

- Show the target job's structured title and short description read-only so the applicant can confirm what they are applying for.
- Add a multiline field labeled **Application Description** or **Why are you a good fit?**.
- Placeholder: **Write a short message to the employer…**.
- This is the applicant's cover note/motivation, not a replacement for structured job data or the CV.
- Preserve line breaks, trim surrounding whitespace, and enforce a documented length such as 20–2,000 characters.
- Do not render the note as HTML.
- Make the field required only if product/backend policy requires it; otherwise clearly mark it Optional.
- Preserve the draft through document pickers and failed submissions.

### 4. Flexible whitespace

- Preserve the spacious, uncluttered composition from the reference.
- Use flexible layout constraints/`Spacer`, not fixed vertical coordinates.
- On short screens or with errors/file preview, allow the page content to scroll.

### 5. CV upload zone

Match the large dashed rounded rectangle:

- Centered gray cloud-upload icon.
- Primary copy:
  - Mobile: **Tap to upload**.
  - Pointer/desktop: **Drag & drop or tap to upload**.
- Secondary copy is generated from the actual backend policy, for example:
  - **PDF, DOC or DOCX (max. 10 MB)** under the current file-service contract.
- The supplied image says **JPG, PNG, or PDF (Max 5MB)**. Do not display this copy while the backend rejects JPG/PNG. If scanned-image CVs are approved, extend the backend `CV` MIME whitelist first and then display the configured 5 MB policy.
- Entire zone is tappable and keyboard accessible.
- Use a privacy-preserving file picker and request no broad storage permission when the platform picker can grant access to the chosen file.

### 6. Selected CV state

After selection, replace or supplement the upload prompt with a file card showing:

- File-type icon.
- Safe filename.
- Formatted file size.
- Selected/saved CV label where relevant.
- Actions: **Preview/Open**, **Replace**, and **Remove**.
- Validation/upload error directly beneath the card.

Do not show the full local filesystem path. A selected file is not uploaded until Submit unless the architecture explicitly uses a managed temporary upload.

### 7. Submit action

- Full-width teal rounded **Submit** button below the upload area, matching the reference.
- Preserve at least `44 px` logical height.
- Disabled until:
  - Job is loaded and eligible.
  - Application Description is valid when required.
  - A valid local or saved CV is selected.
  - No submission/upload is running.
- During upload/application creation, keep dimensions stable and show clear stage/progress text such as **Uploading CV…** then **Submitting application…**.

## Saved CV support

The career-service provides `GET /api/v1/users/me/cv` and `PUT /api/v1/users/me/cv`.

- On entry, load current saved CV metadata in parallel with job validation.
- If a saved CV exists, allow it to appear as the selected CV or as a compact **Use saved CV** choice without disrupting the reference layout.
- Selecting a saved CV uses its existing authorized `cv_file_id` and skips re-upload.
- Uploading for one application must not silently replace the user's default CV. Offer **Save as my default CV** only as an explicit optional choice and call `PUT /users/me/cv` after upload when selected.
- If saved CV metadata points to a missing/forbidden file, clear that UI selection and request a replacement.

## Update CV and document behavior

Provide explicit, distinct choices:

- **Use saved CV** — apply with the current default document without uploading.
- **Update CV** — choose a replacement document, upload it, and set it as the user's new default only after explicit confirmation.
- **Upload for this application only** — choose a document for this job without changing the saved default.
- **Replace document** — change the selected local file before Submit.
- **Remove** — clear the current local selection and return to saved/no-file state.

Never overwrite the user's saved CV merely because they selected a different document for one application. If Update CV is chosen, show the existing and replacement filenames and require an explicit **Use as my default CV** choice.

## Accepted file policy

Use server-driven/configured policy as the source of truth.

Current documented file-service CV whitelist:

- `application/pdf`.
- `application/msword` (`.doc`).
- DOCX MIME (`.docx`).

Recommended initial client maximum: `10 MB`, unless the backend publishes a different value.

Validation:

- Validate extension for picker convenience, but verify MIME/content signature rather than trusting filename.
- Reject empty, corrupt, encrypted/unsupported, oversized, or wrong-type files with an actionable message.
- Sanitize filename for display/upload while preserving a user-friendly name.
- Server repeats every validation and malware scanning; client validation is only early feedback.
- For privacy and compatibility, PDF is preferred but not required under the current contract.

If product insists on the reference policy `JPG/PNG/PDF, max 5 MB`, update file-service's private CV whitelist, reviewer rendering, and security tests before enabling image CVs. Do not upload them as `POSTER` merely to bypass CV rules.

## Job eligibility checks

Before enabling Submit, validate authoritative job/application state:

- Post exists.
- Post type is `JOB`.
- Job is open and published.
- Deadline has not passed.
- Application limit has not been reached when that feature exists.
- Current user is not the job author.
- Current user has not already applied.

The backend is authoritative and repeats all checks atomically during application creation. Client checks improve UX but do not prevent races.

Possible entry states:

| State | UI behavior |
|---|---|
| Eligible | Show upload/select and Submit |
| Already applied | Show **Application already submitted**, update origin to Applied, offer View Application/Back |
| Closed/expired/full | Disable upload/Submit and explain |
| Own job | Explain that creators manage applicants instead of applying |
| Job missing/forbidden | Show unavailable state and Back |

## Submission pipeline

Use an explicit guarded state machine:

`loadingJob → ready → validating → uploadingCv → applying → success` or `error`.

### New local CV

1. Freeze `jobPostId`, application description, selected file metadata, and default-CV preference in an immutable snapshot.
2. Revalidate form/job state.
3. Generate/reuse an idempotency key for this attempt.
4. Upload once:
   - `POST /api/v1/files/upload`.
   - Multipart `file`.
   - `type=CV`.
5. Receive authoritative `file_id`, filename, MIME, size.
6. If explicitly requested, set as default via `PUT /api/v1/users/me/cv`.
7. Submit application:
   - `POST /api/v1/job-applications`.
   - `{ "job_post_id": "...", "cv_file_id": "...", "application_note": "..." }` when the extended contract is enabled.
8. Reconcile application response and show success.

### Existing saved CV

1. Validate selected saved `cv_file_id` still exists and belongs to the current user.
2. Skip upload.
3. Submit the same job-application request.

### Retry rules

- If upload succeeds but application creation fails, preserve/reuse the uploaded `cv_file_id`; never upload another duplicate on Retry.
- Duplicate Submit taps never launch parallel uploads/applications.
- If the backend returns duplicate application `409`, reconcile as Already Applied rather than encouraging another retry.
- Define orphan CV cleanup for uploads never attached to an application/default CV; do not delete a file that another application references.

## Application success

After `201 Created`, show a confirmation dialog/sheet:

- Success icon.
- Title: **Application submitted**.
- Message: **Your CV was sent for {job title}.**
- Primary action: **Done**.
- Optional **View application** only when its route is implemented.

Return a typed result:

```dart
ApplyCvResult(
  jobPostId: jobPostId,
  applicationId: response.applicationId,
  status: JobApplicationStatus.pending,
)
```

Home/Post Detail consumes the result and updates the matching job card from **Apply** to **Applied** by stable `jobPostId`, without refreshing or mutating unrelated cards. A background refresh reconciles authoritative state.

Use `Get.back(result: applyCvResult)` only after success is acknowledged. Preserve Home scroll position.

## API contracts

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/posts/{jobPostId}` | Load/validate structured job post |
| `GET` | `/api/v1/job-applications` | Determine current user's application state efficiently |
| `GET` | `/api/v1/users/me/cv` | Load saved CV metadata |
| `POST` | `/api/v1/files/upload` | Private CV upload |
| `PUT` | `/api/v1/users/me/cv` | Explicitly set default CV |
| `POST` | `/api/v1/job-applications` | Create application |

Application request:

```json
{
  "job_post_id": "uuid",
  "cv_file_id": "uuid",
  "application_note": "I’m interested in this role because…"
}
```

The current career-service request only documents `job_post_id` and `cv_file_id`. Feature-gate the Application Description field or extend the backend entity/request/response before claiming it was delivered to the employer. Never silently discard the user's note.

Expected successful state includes `application_id`, `job_post_id`, `cv_file_id/name`, `status: PENDING`, and `applied_at`.

## Backend contract gaps and required clarifications

1. The Home feed/post response does not currently include `has_applied`/application state. Add it or provide an efficient current-user lookup; do not make one request per Home card.
2. Job deadline/application-limit/open-state enforcement must be authoritative. The application-limit feature from `../../media/03.create_poster.md` is not yet defined in career-service.
3. Define idempotency for upload/application retries in addition to the unique `(job_post_id, applicant_id)` constraint.
4. Define orphan CV retention/cleanup.
5. File-service download currently focuses on owner/public-post access. Authorized job authors/reviewers need a secure, audited CV-access path through career-service; CV files must never become public merely because they are attached to an application.
6. If JPG/PNG CVs are required by the image copy, extend the `CV` MIME contract rather than misclassifying files.
7. Add `application_note`/cover-description storage, length validation, privacy, applicant/owner visibility, and response mapping if the written description is enabled.

## Privacy and security

- CVs are private personal documents.
- Store in the private `cvs` bucket/category and use authenticated, short-lived access.
- Only the applicant and authorized owner/reviewer of the target job can access a submitted CV.
- Do not expose CV URL/file ID in analytics, logs, notifications, or public post payloads.
- Never parse a poster QR code to decide where to send a CV.
- Do not email/upload the CV to arbitrary addresses or third-party links from poster content.
- Malware scan and audit reviewer access server-side.
- Clear temporary local copies according to platform/file-picker policy and on logout/account switch.

## Loading and error handling

- Job loading error: Retry/Back; Submit disabled.
- Picker cancelled: remain ready without showing an error.
- Invalid file: retain screen/job context and explain accepted policy.
- Upload failure: keep local selection and offer Retry/Replace.
- Apply failure after upload: keep uploaded file ID and retry only application creation.
- `403`: distinguish own-job/not eligible from auth problems using safe error codes.
- `404`: job/file unavailable; request replacement or return safely.
- `409`: Already Applied; reconcile origin card.
- `422`/closed/full: show no-longer-accepting state.
- `502`: upstream unavailable; keep reusable uploaded file and allow Retry.
- `401`: global token refresh/reauthentication while preserving non-sensitive draft metadata.
- Never show raw stack traces, storage paths, signed URLs, or backend response bodies.

## Back/discard behavior

- Before upload, Back simply discards the local selection after confirmation when needed.
- During upload/application, prevent accidental double navigation; allow safe cancellation only when supported.
- After successful upload but before application success, preserve the file reference for retry and explain before abandoning.
- Leaving the screen never creates an application implicitly.

## Accessibility and responsive behavior

- Label Back, job context, upload zone, selected CV, Preview/Replace/Remove, Submit, progress, errors, and success actions.
- Announce accepted types/size and submission stages.
- Ensure `44 × 44` targets.
- Support keyboard activation and drag/drop on pointer platforms.
- Keep button/upload/file card usable at `320 px`, with large text and long filenames.
- Truncate visible filenames with ellipsis while exposing the full safe filename through semantics.
- Do not rely on teal/gray color alone for enabled, uploading, success, or failure states.

## Controller responsibilities

- Parse/validate `ApplyCvArgs`.
- Load job eligibility and saved CV in parallel.
- Maintain and validate the application-description draft.
- Pick/validate/preview/replace/remove local CV.
- Select existing saved CV.
- Distinguish saved CV, update-default CV, and application-only document modes.
- Manage explicit set-default preference.
- Submit through one guarded upload→apply pipeline.
- Preserve uploaded file ID across Retry.
- Map backend error codes to actionable UI states.
- Return `ApplyCvResult` and update origin state.
- Dispose resources and ignore stale responses after navigation.

## Testing and acceptance criteria

- Screen visually matches `upload_cv.png`: Upload CV header, compact context, dashed upload zone, and full-width Submit.
- Apply from a job card opens the screen with the exact canonical `jobPostId` and does not open Post Detail.
- Job title/author are loaded from structured data, not poster OCR/QR/text parsing.
- Job description is shown read-only and the applicant's Application Description is validated/preserved/submitted only when the backend supports it.
- Submit is disabled for unknown, closed, expired, full, own, or already-applied jobs.
- Current backend PDF/DOC/DOCX policy is displayed accurately; JPG/PNG is never offered unless backend CV support exists.
- Local and saved CV paths both submit the correct `cv_file_id`.
- Update CV replaces the default only with explicit consent; application-only uploads never overwrite it.
- Upload→application pipeline handles progress, Retry, and idempotency without duplicate files/applications.
- `409` reconciles to Applied; success updates only the matching Home/Post Detail job.
- CV remains private and reviewer access is authorized/audited.
- Picker cancellation, invalid/oversized file, upload error, apply error, auth expiry, upstream error, and job-state race are tested.
- No overflow occurs on small phones, large text, long job titles, or long filenames.
