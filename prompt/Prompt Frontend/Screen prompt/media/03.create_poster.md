# 03 - Create Poster, Video, and Job Post Prompt

Build the **Create Post** flow for the Vithey App in Flutter. It must support:

- A Facebook-style **regular poster post** for community/social content.
- A LinkedIn-style **job poster post** with structured job data, an Apply action, application limits, and optional scheduling.

All created types must map directly into the mixed Home feed defined by `01-home-prompt.md` and its card prompts.

## Goal

Allow a user to create an image-based social poster, a video post, or a structured job poster; choose the permitted audience; preview/change media; optionally schedule publishing; and publish once. A successful immediate post appears at the top of the correct Home feed without requiring an app restart.

## End-to-end flow

1. User opens Create from the Home composer, gallery shortcut, or center Create navigation action.
2. Show the post-type selector if no type was supplied by the entry intent.
3. User selects Poster or Job and taps **Next**.
4. Open the main **Post Setting** composer with the selected type.
5. User writes content, selects an audience, chooses/previews media, and optionally schedules.
6. Job mode also collects structured job fields and the maximum number of CV applications.
7. User taps **Post**.
8. Validate the immutable submission snapshot.
9. Upload media once through file-service.
10. Create the typed post through content-service with the uploaded `media_file_id`.
11. Return the normalized created post to Home.
12. Home inserts an immediately published post at the top if it belongs in the current feed; scheduled posts do not appear until published by the server.

- Three full-width rows with leading icons and trailing radio indicators:
  1. **Poster** — image/poster icon.

## Audience selector

Match `post type.png`; despite the filename, this sheet chooses visibility, not post type.

- Heading: **Who can see your post?**
- Rounded bottom sheet with drag handle.
- Three full-width rows with leading icons, label/description, and trailing radio:

| Value | Label | Description |
|---|---|---|
| `PUBLIC` | Public | Visible for everyone |
| `FRIENDS` | Friends | Only friends can see this post |
| `PRIVATE` | Only Me | Only visible in my account |

- Default regular Poster audience: use the last valid user choice or `PUBLIC` according to product policy.
- Composer summary label for `PUBLIC` may read **Everyone**, matching the main reference.
- Job posts must be `PUBLIC`/Everyone so they can appear as job opportunities in Home. Disable Friends/Only Me with a clear explanation in Job mode rather than silently changing the user's selection at submit time.
- Visibility must be enforced server-side in feed/detail APIs. Client filtering alone is not security.

## Regular Poster mode — Facebook-style

Required data:

- `type: POSTER`.
- Audience/visibility.
- Caption/content according to product minimum rules.
- One image/poster media file for the reference design.
- Optional `scheduled_at`.

Behavior:

- A regular Poster is social/community content, not a job.
- Do not show CV limit, job title, deadline, requirements, or Apply settings.
- Upload the image with file type `POSTER`.
- Create a `POSTER` post referencing the returned file ID.
- On Home, render it through `PosterPostCard` with author, timestamp, content, uncropped image, engagement footer, and Follow behavior for other users.
- The author viewing their own newly created card must not see a self-Follow button.
- Public posters can appear in eligible Home feeds. Friends/private posters must follow backend visibility rules and must never leak into unauthorized feeds.

## Video mode — social video post

Required data:

- `type: VIDEO`.
- Audience/visibility.
- Caption/content according to product rules.
- One supported video file.
- Optional generated/uploaded thumbnail when the backend contract supports it.
- Optional `scheduled_at`.

Behavior:

- Show video-specific picker copy and validate duration, size, MIME, and codec/container policy.
- Current file-service supports `video/mp4` and `video/quicktime`; generate picker options from the server-configured policy.
- Display an inline preview with play/pause, duration, replace, and remove controls. Do not autoplay while editing.
- Upload with `type=VIDEO` and show determinate progress when byte progress is available.
- Keep CV limit and job metadata hidden.
- On Home/Profile, dispatch the created item to `VideoPostCard` from `card_poster/02.poster_video.md`.
- Video playback in feed starts muted, never auto-plays multiple cards, respects reduced motion/data saver, and releases controllers when off-screen.
- If thumbnail/transcoding/processing is asynchronous, return and render a typed `PROCESSING` state; never pretend the video is playable before the server says it is ready.

## Job Poster mode — LinkedIn-style

Job mode combines the visual poster upload with structured job metadata. Do not make the hiring image the only source of job information.

Required structured fields:

- Job title.
- Short description/content.
- Requirements/qualifications.
- Application deadline.
- Maximum CV applications.
- Public audience.
- Hiring poster image for this reference design.

Optional fields only if supported by the documented contract:

- Company/location.
- Employment type.
- Salary range.
- Contact/application instructions.

Use a compact expandable job-details form or a dedicated step/sheet built with `CustomTextField`; keep the main composer visually faithful. The content shown in the Home card comes from structured values plus caption, not OCR of the uploaded poster.

On Home:

- Render through `JobPosterCard`.
- Show organization/author, timestamp, job announcement text, hiring image, engagement counts, and **Apply** for eligible viewers.
- Pass the canonical `jobPostId` to `Routes.APPLY_CV`.
- The creator sees applicant-management state rather than applying to their own job when that route is available.
- Deadline and application limit are enforced by the backend. Once either closes the job, Home displays **Closed** and blocks new applications.

## Scheduling

Match `set schedule.png`, `set date.png`, and `set hour.png`.

### Schedule sheet

- Rounded bottom sheet with drag handle.
- Heading: **Schedule**.
- Required Date and Time fields with calendar/clock icons.
- Display the effective timezone, e.g. **UTC+7:00, based on your location**.
- Bottom actions: teal **Clear** and **Next**.
- Next remains disabled until both date and time are valid.

### Date/time pickers

- Use platform/themed date and time pickers matching the teal reference.
- Only allow a future publish instant; reject elapsed times after timezone conversion.
- Store/send an ISO-8601 UTC instant, while displaying the user's local timezone.
- Handle daylight/timezone changes and revalidate immediately before submission.
- Clear removes scheduling and returns the post to immediate publishing.

### Scheduled-post behavior

- The server—not a local timer—owns scheduled publication.
- A successful scheduled submission returns a scheduled state and must not be inserted into the public Home list before its publish time.
- Show confirmation such as **Post scheduled for {local date/time}** and route to a scheduled-post management view if one exists; otherwise return Home without fabricating a live card.

## Validation matrix

| Rule | Poster | Video | Job |
|---|---:|---:|---:|
| Valid authenticated author | Required | Required | Required |
| Audience | Required | Required | Public only |
| Caption/content | Required by product rule | Required by product rule | Required |
| Poster image | Required | No | Required |
| Video file | No | Required | No |
| Structured title | No | No | Required |
| Requirements | No | No | Required |
| Deadline | No | No | Required and future |
| CV application limit | No | No | Required, positive integer |
| Scheduled time | Optional, future | Optional, future | Optional, future and not after deadline |

Show validation inline near the relevant control and focus/scroll to the first invalid field. Never begin media upload when form validation already fails.

## Submission pipeline

Use an explicit state machine: `editing → validating → preparingMedia → uploadingMedia → creatingPost → success` or `failure`.

1. Freeze an immutable draft snapshot so type/audience/media cannot change mid-submit.
2. Validate fields and session.
3. Generate/reuse an idempotency key across retries.
4. Upload selected media once:
   - `POST /api/v1/files/upload`
   - Multipart field `file`.
   - Type `POSTER` for regular and job-poster images unless a documented `JOB_POSTER` file type is added.
   - Type `VIDEO` for video media.
5. Receive `file_id` and URL.
6. Create the typed post through `POST /api/v1/posts`.
7. Reconcile the normalized server response.
8. On immediate success, return `CreatedPostResult(post)` to Home.
9. On scheduled success, return `CreatedPostResult.scheduled(...)` without inserting a live card.
10. Clear local draft only after the terminal successful result or explicit discard.

If upload succeeds but post creation fails, retry creation with the same uploaded file ID and idempotency key. Do not upload duplicate files on every retry. Define orphan-file cleanup with the backend.

## Current backend contract gaps

The current content-service contract supports `POSTER`, `VIDEO`, and `JOB`, but it does not fully support this reference flow. Resolve these gaps rather than dropping data or inventing client-only behavior:

1. **Job media:** the JOB creation example lacks `media_file_id`, while Home requires a hiring-poster image. Document and support media on JOB posts.
2. **Visibility:** Public/Friends/Only Me is not defined on the current Post entity/API. Add server-side visibility and authorization rules before enabling non-public choices.
3. **Scheduling:** `scheduled_at`, scheduled status, server publication, editing/canceling, and feed exclusion are not defined.
4. **Application limit:** career/content contracts do not define `application_limit` or atomic enforcement.
5. **Job lifecycle:** define OPEN/CLOSED/EXPIRED and whether limit/deadline automatically transition state.
6. **Idempotency:** upload/create retry behavior and orphan-file cleanup require a contract.

Feature-gate unsupported options in production. Do not show a control that appears to save a value the backend discards.

## Home-feed integration

On immediate success, return a normalized `FeedPost` compatible with `01-home-prompt.md`:

- `POSTER` becomes `PosterFeedPost` / `PosterPostCard`.
- `VIDEO` becomes `VideoFeedPost` / `VideoPostCard`.
- `JOB` becomes `JobFeedPost` / `JobPosterCard`.

Home behavior:

1. Receive the created result from Create Post.
2. Confirm it is immediately published and visible in the current feed/audience.
3. Upsert by `post_id` at index `0`; never insert a duplicate.
4. Preserve current feed state and scroll to/show the new card according to product behavior.
5. Refresh in the background to reconcile server ordering and derived fields.
6. Scheduled/private posts that do not belong in the current Home feed are not inserted.

The client must dispatch by `type`, never by whether a caption contains “job” or an image looks like a hiring poster.

## Draft and discard behavior

- Autosave a non-sensitive local draft per post type while editing.
- Preserve caption, structured job fields, selected local media reference where valid, audience, limit, and schedule.
- On Back with meaningful changes, offer **Save draft**, **Discard**, and **Continue editing**.
- Do not retain temporary media longer than necessary.
- Clear drafts after successful publication or explicit discard.
- A draft is not a published post and must never appear in Home.

## Error handling

- Permission denied: explain how to select media or open settings without blocking text editing.
- Invalid media: retain the rest of the draft and request a replacement.
- Upload failure: show retry; do not create a post without required media.
- Create failure after upload: reuse uploaded `file_id` on retry.
- Session expiration: preserve the draft, reauthenticate through the global flow, and safely resume if supported.
- Deadline/limit conflict from server: show field-specific error and return to editing.
- Scheduled time elapsed: prompt user to choose a new time or publish now.
- Never expose raw stack traces, storage paths, tokens, or backend bodies.

## Accessibility

- Label Back, Post, audience, type, editor, media preview/remove, CV limit, gallery, schedule, every sheet choice, date/time fields, and progress state.
- Announce selected radio values and disabled reasons.
- Ensure interactive targets are at least `44 × 44 logical pixels`.
- Keep focus order logical and restore focus after closing sheets.
- Provide meaningful media-preview semantics from the caption/job title rather than OCR output.
- Do not rely on color alone for selected, error, scheduled, or disabled states.
- Support keyboard Send/Done actions without accidentally publishing.

## Responsive and performance requirements

- Support phones down to `320 px` wide without overflow.
- Keep composer usable with the software keyboard open and large text scaling.
- Use safe areas and constrain content width on tablets.
- Load picker thumbnails efficiently and dispose image/scroll/text controllers.
- Compress/resize upload copies according to backend policy without degrading readable poster text.
- Show determinate upload progress where the client can measure bytes.
- Do not decode full-size gallery images merely to render thumbnails.

## Controller responsibilities

- Initialize from an optional entry intent (`poster`, `job`, `video`, or gallery shortcut).
- Maintain immutable/observable draft fields.
- Open/select type and audience.
- Pick, validate, preview, replace, and remove media.
- Edit/validate structured job metadata.
- Select/validate application limit.
- Set/clear date, time, and timezone-aware schedule.
- Save/restore/discard drafts.
- Submit through one guarded state machine with retry/idempotency.
- Return normalized immediate/scheduled results to Home.
- Dispose all resources and cancel safe in-flight preparation when leaving.

## Testing and acceptance criteria

- Main composer matches `create poster.png`, including Post Setting app bar, author/audience/type row, editor, toolbar, keyboard behavior, and Post action.
- Type sheet matches `type of poster.png`; audience sheet matches `post type.png`.
- Media albums, photo grid, replacement sheet, and full preview match their references.
- Schedule summary/date/time flows match the references and preserve timezone correctness.
- CV limit sheet appears only for Job and validates preset/custom limits.
- Regular Poster submission uploads media, creates type `POSTER`, and renders through Home's regular poster card.
- Job submission sends structured `job_meta` plus poster media, creates type `JOB`, and renders through Home's job card with Apply state.
- Switching types never leaks job fields into Poster payloads or silently destroys data.
- Job posts are public; unauthorized Friends/Only Me selections cannot be submitted.
- Immediate success upserts once at the top of the eligible Home feed.
- Scheduled/private results do not appear incorrectly in Home.
- Duplicate Post taps and retries do not create duplicate uploads/posts.
- Upload-success/create-failure retry reuses the uploaded file.
- Validation, permissions, image failure, upload progress/error, API failure, draft restore/discard, and auth expiry are tested.
- No overflow occurs on small screens, large text, keyboard open, long content, or tall poster previews.
